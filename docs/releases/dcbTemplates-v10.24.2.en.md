# DCB templates 10.24.2

The five starter templates for Sekiban DCB 10.24.2. Generated projects reference the 10.24.2 packages and Orleans 10.4.2. There are no 10.24.0 or 10.24.1 template releases; these notes cover the changes since templates 10.23.4.

## Library changes included

- 10.24.0: generated projects get Orleans 10.4.2. Read the 10.24.0 library release notes before you upgrade a running system: the whole Orleans cluster must be upgraded together, some Orleans metric names changed, and existing PostgreSQL databases created with the Orleans scripts need the non-destructive upgrade steps in the deployment guide.
- 10.24.1: a dependency security update of the libraries. `Sekiban.Dcb.Sqlite` no longer brings the vulnerable `SQLitePCLRaw.lib.e_sqlite3` 2.1.11, and `Sekiban.Dcb.CosmosDb` no longer brings the vulnerable `Microsoft.AspNetCore.WebUtilities` 2.3.0. See the 10.24.1 library release notes.
- 10.24.2: fixes for multi-projection snapshot restore and persistence, for full rebuilds that start while the grain is running, and for a grain whose checkpoint save was rejected because another writer had invalidated the checkpoint. The public API and the dependencies are unchanged since 10.24.1. See the 10.24.2 library release notes.

## Template changes

- The templates use current dependency versions: Aspire 13.6.5, OpenTelemetry 1.20, ASP.NET Core, EF Core and Microsoft.Extensions 10.0.15, Microsoft.Extensions.Http.Resilience and ServiceDiscovery 10.11.0, Scalar 2.20.0, and newer patch or minor versions of the other packages.
- A new project builds without known-vulnerability warnings. The earlier versions brought vulnerable MessagePack, Microsoft.OpenApi and OpenTelemetry packages, and the libraries before 10.24.1 brought vulnerable SQLite and WebUtilities packages.
- The two AWS templates (`sekiban-dcb-orleans-aws`, `sekiban-dcb-decider-aws`) ship the Orleans 10.4.2 PostgreSQL scripts in `ApiService/SqlScripts`: `PostgreSQL-Clustering.sql` updates the membership functions and the dead-silo cleanup query, and `PostgreSQL-Persistence.sql` uses `timestamptz`/`now()` and adds the `DeleteStorageKey` query. New databases get this schema.
- A new project builds without compiler warnings. The API service no longer calls the deprecated `WithOpenApi()`; the OpenAPI document still describes the endpoints. If a required Event Hub or storage connection setting is missing, the API service now stops at startup with a message that names the setting.
- Decider template: the API service is now reported healthy and both web front ends start. Before, the AppHost checked health on an HTTPS endpoint that the API service does not listen on, so the API service stayed unhealthy and the web front ends waited for it. The Blazor front end is now reachable from the dashboard link.
- The `http` launch profile of every AppHost sets `ASPIRE_ALLOW_UNSECURED_TRANSPORT`, so `dotnet run --launch-profile http` starts.
- The AppHost projects set `AspireUseCliBundle` to `true`, as Aspire 13.6 recommends. `dotnet run` of an AppHost now starts it through the Aspire CLI. If the `aspire` command (13.5.0 or later) is not installed, the build gets the matching Aspire CLI through `dnx`.
- The API service sets the Orleans activation timeout (`GrainCollectionOptions.ActivationTimeout`) to 5 minutes. Restoring a large multi-projection snapshot can take longer than the default 30 seconds; with the default, each activation then fails.
- The API service sets `FirstQueryCatchUpMaxWaitMs` to 5,000 milliseconds. While a projection catches up, for example after a restart or during a full rebuild, a query waits up to 5 seconds for the catch-up and then gets HTTP 503 with a `Retry-After` header, instead of waiting until all events are replayed. The 5 seconds do not include activating the projection (for example restoring a large snapshot) or waiting for the grain to take the request. The value is below the 10-second attempt timeout of the generated web front ends' HTTP clients, which retry a 503 automatically with their standard resilience settings. Retry such a request later.

## Existing projects

Updating the template package does not change a project you already generated. To take the library changes, set `SekibanDcbVersion` to `10.24.2` and `MicrosoftOrleansVersion` to `10.4.2` in `SekibanDcbTemplateVersion.props`. To fix the vulnerability warnings, update the same packages as above. If restore then fails with NU1605 (package downgrade), raise the reported direct references to at least the versions in the 10.24.1 library release notes. In a project generated from an AWS template, also copy `ApiService/SqlScripts/PostgreSQL-Clustering.sql` and `PostgreSQL-Persistence.sql` from a newly generated project, and upgrade an existing database with the "Orleans 10.4.2 PostgreSQL upgrade" steps in the deployment guide (`docs/dcb_llm/16_deployment.md`); do not reinitialize it, which drops grain state. To take the two new settings, add `siloBuilder.Configure<GrainCollectionOptions>(options => options.ActivationTimeout = TimeSpan.FromMinutes(5))` to the Orleans configuration of the API service, and set `FirstQueryCatchUpMaxWaitMs = 5000` in its `GeneralMultiProjectionActorOptions`; with the second setting, handle the catch-up-in-progress error as a retryable response (a newly generated project maps it to HTTP 503).
