# Sekiban DCB 10.23.2

- バージョン: `10.23.2`。DCB ライブラリは 26 パッケージです。net9.0 と net10.0 を対象とし、`Microsoft.Orleans.*` は 10.3.1 のままです。
- データやスキーマの移行は不要で、公開 API の変更もありません。cold event の hybrid read を使っているアプリケーションには、動作の変更が 1 件あります。「アップグレード前の確認」をご覧ください。hybrid read を使っていないアプリケーションは、この変更の影響を受けません。

## 変更

- **サービスごとに作られるストアも cold event を読むようになりました**（issue #1322）。これまで `AddSekibanDcbColdEventHybridRead()` は、登録済みの `IEventStore` だけを置き換えていました。今回から、登録済みの `IEventStoreFactory` も包むので、サービスを指定して作られるストアは、cold のセグメントを読んでから hot の末尾を読みます。対象は、通常の materialized view の catch-up（PostgreSQL、SQL Server、MySQL、SQLite）、durable subscription、factory からストアを取得する multi-projection の catch-up です。これまでは、cold event を有効にしていても、これらは hot のストアだけを読んでいました。
- **cold event を小さなバッチで読んでも、各セグメントを 1 回だけ読むようになりました。** 件数の上限を指定する一覧の読み取り（`ReadAllSerializableEventsAsync`）が cold のセグメントの途中で止まった場合、そのセグメントの残りをメモリに保持し、続きの読み取りに使います。10 万件のセグメントを 100 件ずつ読む場合、これまではセグメントを 1,000 回開いていましたが、今回から 1 回になります。これは呼び出し回数を数えるテスト用のストレージで確かめた値で、所要時間は計測していません。

## 修正

- **DynamoDB: テーブルの自動作成が、同時に作成する別の呼び出しがあっても失敗しなくなりました。** 2 つの呼び出しがどちらも「テーブルがない」と判断して作成すると、後の呼び出しが `ResourceInUseException` で失敗していました。その呼び出しが起動時の初期化だった場合、アプリケーションは起動しませんでした。空のストレージに対する最初の起動で、1 つのプロセスの中でも、同時に起動する複数のインスタンスの間でも起こり得ました。今回から、後の呼び出しは、テーブルが使用可能になるまで待ちます。

## アップグレード前の確認

`AddSekibanDcbColdEventHybridRead()` を呼んでいるアプリケーションだけが対象です。

- **factory を使う処理が cold を読むようになります。** 切り替える設定はありません。イベントストアのプロバイダーは、`AddSekibanDcbColdEventHybridRead()` より前に登録してください。包まれるのは、その時点で最後に登録されている `IEventStoreFactory` です。後から登録したものは包まれません。1 つも登録されていない場合は、何も包まれず、エラーにもなりません。
- **メモリ。** 一覧の読み取りを使うホスト（materialized view、durable subscription、件数の上限を指定する独自の呼び出し）は、解析済みの cold event をメモリに保持するようになります。factory 経由で読むサービスごとに最大 1 セグメント、これとは別に、単一の `IEventStore` に 1 セグメントです。1 セグメントは最大 `SegmentMaxEvents` 件（既定は 10 万件）です。`SegmentMaxBytes`（既定は 512 MB）は、エクスポート時のセグメントの payload のバイト数の上限で、読み取り側のメモリの上限ではありません。解析済みのイベントは、payload のバイト数より多くのメモリを使います。加えて、保持されたセグメントを使えない読み取りは、実行中にセグメント全体を解析します。同時に行われる読み取りは、それぞれが解析します。保持されたセグメントは、最後まで読んだときと、2 分間使われなかったときに解放します。後者は、同じストアの次の一覧の読み取りのときに確かめます。同じサービスで、異なるセグメントを交互に読む場合は効果がなく、読み取りのたびにセグメント全体を解析します。これらのホストのメモリは、エクスポートするセグメントの大きさに合わせて見積もってください。
- **cold があるのは、エクスポートを実行しているサービスだけです。** それ以外のサービスのストアは、マニフェストが見つからないので、これまでどおり hot を読みます。
- **失敗時の動作。** これまでどおり、cold のセグメントを開けない、または解析できない場合、その読み取りは同じ位置から hot のストアを読みます。失敗した読み取りで materialized view のチェックポイントが進むことはありません。変わった点は 2 つです。セグメントの中の壊れた行は、要求した範囲の外にあっても、その読み取りを hot に切り替えます。また、マニフェストを読み込めない（デシリアライズできない）場合、読み取りは例外を送出します。この例外は、今回から materialized view と durable subscription にも届きます。なお、これまでと同じく、hybrid read は cold のストレージが完全であることを検証しません。セグメントの間に欠落があるマニフェストや、解析はできるものの、マニフェストの記載より件数の少ないセグメントは検出されず、読み取りはその先へ進みます。今回から cold を読むようになる処理は、これまで hot のストアからすべてのイベントを読んでいましたが、今後は、エクスポートされたセグメントが正しいことを前提にします。
- **factory 経由の multi-projection の catch-up** は、単一のストア経由の catch-up と同じく、`ColdCatchUpBatchSize` と、セグメント境界でのスナップショットを使うようになります。

## ドキュメント

- `docs/dcb_llm/19_cold_events.md` と `20_materialized_view.md`（英語と日本語）に、factory から作られるストアの hybrid read、保持されるセグメント、失敗時の方針を記載しました。cold event の章にあった「hybrid read はイベント ID で重複を除いて並べ替える」という記述を改めました。実際には、cold の境界で読み分けます。
