# DCB テンプレート 10.23.2

Sekiban DCB 10.23.2 用の 5 つのスターターテンプレートです。生成されるプロジェクトは 10.23.2 のパッケージを参照します。

## 予約のサンプル: ルールを回避できる問題の修正（Decider テンプレート）

Decider テンプレートの会議室予約のサンプルには、サンプル自身のルールを呼び出し側が回避できる問題がありました。10.22.0 と 10.23.1 のテンプレートのパッケージに含まれています（10.23.0 のテンプレートのパッケージはありません）。それより前のバージョンは確認していません。問題があるのはサンプルアプリケーションのコードで、Sekiban のライブラリではありません。**テンプレートのパッケージを更新しても、生成済みのプロジェクトは変わりません。Decider テンプレートから始めたプロジェクトには、同じ修正を適用してください。** 変更の内容は https://github.com/J-Tech-Japan/Sekiban/pull/1330 にあります。

- **Decider.Aws: 主催者をリクエストの本文から受け取っていました。** `POST /api/reservations/draft` は本文の `organizerId` をそのまま使い、`POST /api/reservations/quick` は、ユーザー ID のクレームが不正な場合に ID を新しく作っていました。コマンドのハンドラーは、管理者の例外、予約できる月の範囲、月間の上限を、この ID で判定します。そのため、サインインしたユーザーが管理者の ID を送ってルールを回避したり、別のユーザーの名義で予約を作成したりできました。今回から、主催者の ID と名前は、サインインしたユーザーのクレームだけから決まります。有効なユーザー ID のクレームがないリクエストは、Decider テンプレートと同じく 401 になります。
- **Decider: クイック予約が月間の上限を確認していませんでした。** Next.js のフロントエンドが既定で使う `POST /api/reservations/quick` は、全員に対して、予約できる月の範囲だけを確認していました。月間の上限に達したユーザーが予約を続けることができ、管理者も月の範囲に制限されていました。今回から、クイック予約と下書きは、共通のヘルパー（`ReservationCreationRules`）で同じルールを適用します。
- **Decider: ベンチマーク用のスイッチを削除しました。** 環境変数 `SEKIBAN_BENCHMARK_SKIP_USER_RESERVATION_RULES` を `true` に設定すると、コマンドのハンドラーは、どの環境でも予約のルールを確認しませんでした。設定 `Benchmark:AllowDebugUserHeaders`（Development 用の設定ファイルで有効で、コード上は環境に結び付いていません）を有効にすると、管理者が `X-Debug-User-Id` ヘッダーで、任意のユーザーとして予約を作成できました。管理者自身のユーザー ID のクレームがない、または不正な場合は、リクエストの本文でも同じことができました。どちらも削除しました。AppHost の `BENCHMARK_PROFILE` と、使われていなかった診断用の設定の受け渡しも削除しました。

## そのほかの変更

- **ヘルスチェックが、実際の状態を確認するようになりました。** 5 つのテンプレートすべてで、`/health` に Orleans のチェックが含まれ、ローカルの silo が active のときだけ正常になります。これまでは、プロセスが起動していれば常に正常で、AWS のテンプレートには Orleans のチェックがありませんでした。Decider テンプレートの `/health` は、認証用データベースの起動時の処理が終わるまで正常になりません。この処理は、Identity のテーブルとロールを用意し、サンプルユーザー（Development）または設定された初期管理者の作成を試みます。AppHost はその後にフロントエンドを起動するので、通常のローカルでの起動では、最初のログインの前にサンプルユーザーが存在します。作成できなかったユーザー（例えば、Identity がパスワードを拒否した初期管理者）はログに記録されますが、`/health` は異常になりません。ログを確認してください。再試行してもデータベースに接続できない場合や、ロールを作成できない場合、`/health` は、インスタンスを再起動するまで異常のままです。同梱の Azure Container Apps と ECS の定義は `/health` を probe して、インスタンスを再起動します。同梱の App Service の定義は health probe を設定していません。ローカルでの実行も再起動されません。`/health` が正常になるまでの時間に、保証された上限はありません。
- **診断用のルートを削除しました。** Base、WithoutResult、WithoutResult.Aws は、`/api/orleans/test` と `/api/health` を公開しなくなりました。これらは、どの環境でも認証なしで利用できました。`/health` と `/alive` を使ってください。
- **拒否された天気のコマンドは 400 を返します**（Decider テンプレート。例えば、予報を 2 回削除すると 500 が返っていました）。
- **`App` という名前のプロジェクトをビルドできます。** `Program` のような C# の型名は、プロジェクト名に使わないでください。
- **Blazor のページ**に、製品名と、このサンプルの説明を表示します。Decider テンプレートのホームページは、会議室のアプリケーションが Next.js のフロントエンドであることを案内します。

## 対象外

テンプレートは cold event を有効にしていません。実際のクラウドへのデプロイ、同梱のインフラ定義の health probe、複数 silo での動作は、このリリースでは確認していません。
